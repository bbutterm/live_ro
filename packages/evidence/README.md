# Offline evidence analyzer — issue #4

Python 3.9+ и системная база IANA timezone; сторонних Python-зависимостей нет.
Только явно переданные JSONL и JSON metadata. Нет подключения к VPS, БД,
reader, shell-командам или автоматического поиска журналов.

```sh
python3 -m packages.evidence --events /private/events.jsonl \
  --metadata /private/metadata.json --now 2026-10-08T09:00:10Z
python3 -m unittest discover -s tests/evidence -v
```

JSON-отчёт идёт в stdout, exit codes: `0 VERIFIED`, `1 FAILED`, `2 UNVERIFIED`.
Для экспорта можно перенаправить stdout в приватный файл вне Git. Отчёт не
копирует raw payload, source_id, пути и значения противоречащих полей.
Содержит только коды причин, объяснения, номера строк/заявок/событий и имена полей.
API: `from packages.evidence import analyze`; `analyze(jsonl, metadata, now=...)`.
Оценочное время обязательно передаёт вызывающий код: результат детерминирован.

## Metadata v1 — локальный интерфейс этого пакета

Это формат offline-входа, не изменение `contracts/witness-v1.md`.
Пример ниже целиком **synthetic**, не свидетельство игры:

```json
{
  "source_id": "synthetic-generation-1",
  "source_type": "rathena_witness",
  "synthetic": true,
  "db_timezone": "Europe/Moscow",
  "window_start": "2026-10-08T09:00:00Z",
  "window_end": "2026-10-08T09:00:01Z",
  "collected_at": "2026-10-08T09:00:02Z",
  "max_age_seconds": 60,
  "id_start": 10,
  "id_end": 10,
  "claims": [
    {"type": "event", "event_id": 10,
     "expected": {"kind": "pos", "char_id": 42, "x": 10}}
  ]
}
```

Соответствующая synthetic JSONL-строка:

```json
{"id":10,"ts":"2026-10-08 12:00:00.000","char_id":42,"kind":"pos","map":"synthetic_map","x":10,"y":20,"a1":null,"a2":null}
```

Все перечисленные metadata обязательны. `source_id` обозначает одну явно
заданную генерацию источника. Смешивание источников/генераций не поддерживается.
`synthetic` — строгий boolean; `source_type` для допустимого свидетельства равен
`rathena_witness`. Это декларация поставщика, не проверка подлинности: программа
не может выявить вымысел, намеренно маркированный как runtime.

Время окна, сбора и оценки должно содержать offset. Требуется
`window_start <= window_end <= collected_at <= now`. Всё окно должно укладываться
в положительный `max_age_seconds`, выбранный вызывающей стороной. Подмена даты
сбора не освежает старые события. VERIFIED означает совпадение наблюдения внутри
этого окна, а не текущее состояние персонажа.

`ts` нормализуется только по явно заданной IANA-зоне. `SYSTEM` не раскрывается
автоматически. Naive `ts` без зоны БД, неоднозначное и несуществующее время DST
дают UNVERIFIED. Aware `ts` не соответствует witness-v1. Дополнительное `ts_utc`,
если передано, сверяется с вычисленным временем; расхождение — FAILED.

`id_start`/`id_end` задают включительные границы ожидаемого интервала одного
источника. Порядок проверяется по ID, не ts; сортировки для исправления порядка
нет. Совпадающие дубликаты дают UNVERIFIED и не добавляют свидетельств;
конфликтующие — FAILED. Разрывы, включая края, дают UNVERIFIED: auto-increment
или фильтрация могут объяснять разрыв, но полнота не доказана. Этот консервативный
срез не подтверждает выборки с разрывами. Проверка огромного диапазона не
материализует список всех отсутствующих ID.

Все десять ключей witness-v1 должны присутствовать. `map`, `x`, `y`, `a1`, `a2`
могут быть null согласно контракту. Неизвестные event kinds, неправильные типы,
bool вместо int и нарушенные диапазоны SQL-полей отвергаются. Дополнительные поля
не используются как свидетельство; `synthetic` на строке всегда блокирует
подтверждение, если значение отличается от false.

## Заявки и статусы

Поддерживается только `type: event`: конкретный `event_id` и `expected` с
обязательными `kind`, `char_id`, опциональными `map`, `x`, `y`. Это проверка
совпадения полей, не причинной связи команды и действия. Любые HP, покупки,
семантика `a1/a2`, body actions, T1–T13 и произвольные итоги не поддерживаются.
Наличие события kill само по себе не подтверждает конкретную цель из a1.

- VERIFIED: все проверки входа пройдены; свежая строка совпала с заявкой.
- FAILED: явное противоречие либо структурно некорректный вход.
- UNVERIFIED: данных или поддержанной семантики недостаточно, включая пустой
  вход, отсутствующий event, synthetic, ACK-source, stale, DST и ID-gap.

Каждая заявка получает объяснение. Ограничения входа блокируют её VERIFIED.
Итоговый приоритет: FAILED > UNVERIFIED > VERIFIED. Противоречие синтетическому
входу может дать FAILED — это ошибка внутри предоставленного набора, не вывод
о реальной игре. Пустой список заявок тоже не даёт VERIFIED.

## Границы приёмки

Все тестовые события вымышлены. Тест положительной ветки намеренно моделирует
`synthetic=false` metadata, но явно помечен synthetic в исходнике и не является
runtime evidence. Пакет не аутентифицирует поставщика, не доказывает полноту
серверной БД, не связывает поколения самостоятельно, не проверяет current live
state и не подтверждает серверные gates. Интеграция, независимый review и
runtime-приёмка остаются за интегратором. Веха B не реализована.
