# Производительность мозга (perf)

Статус: замер и оптимизация такта `Mind.step()` (раз в секунду) после того, как в мозг добавили ~35 модулей.
Цифры — локальные замеры в песочнице (Python 3.11, Linux x86_64, 4 ядра), **на VPS не снимались**: VPS
медленнее, пересчитывать по отношению «до/после», а не по абсолютным мс. Связано с ORG-047 (ресурсы) и
`docs/BRAIN_HOST.md` (N жителей в одном процессе).

## 1. Как мерить

```
cd brain
python3 tools/profile_step.py                        # оба сценария, 1 ч игрового времени (3600 тиков)
python3 tools/profile_step.py --history 14           # память «прожившего» жителя: события за 14 суток (≈ 38 тыс.)
python3 tools/profile_step.py --statements 20        # самые частые SQL-запросы (что повторяется каждый тик)
python3 tools/profile_step.py --cprofile --scenario two
python3 tools/profile_step.py --markdown             # таблицы ниже
```

- **Mind настоящий**, со всеми модулями реестра, `goals.json` и персоны `bot01`/`bot02`; часы реплея
  подменяют `time.time` (как `tests/test_integration.py`).
- Сценарий **day** — один житель на отзывчивом теле `SimBody` (LongDayAllModulesTest): город → охота группой с
  Vera, kill-события, шина мира своя. Сценарий **two** — два жителя в одном городе `TownWorld`
  (TwoResidentsDayTest) на общей шине `world.sqlite`: лекарь, заказы, сделки; цифры **на тик мира**, т. е.
  на двух жителей сразу.
- Тик = `on_message` всех сообщений тела за эту секунду + `mind.step()`. Первые 300 с — прогрев, в замер
  не входят («установившийся режим»).
- SQL считает `sqlite3` trace callback на всех соединениях, которые открыл мозг (память, шина мира);
  коммит — `COMMIT` или запись в соединении без транзакции (autocommit шины). По модулям — обёртка над
  `module.tick` (запросы и время внутри tick модуля); `core` — ядро `step` (life, safety, plans, inbox,
  smalltalk), `on_message` — разбор сообщений тела. «макс мс» — самый долгий одиночный вызов tick модуля.

## 4. Что сделано (поведение не меняется)

1. **Кэш такта** (`Memory.tick()`, `Mind.tick_scope()`): внутри одного `step()` и одного сообщения
   `state` значения `kv` (`mem.get`), отношения (`mem.relation`) и активный план (`PlanStore.active()`)
   читаются из БД один раз. Кэш **сквозной** (запись через методы памяти обновляет/сбрасывает его) и живёт
   только внутри такта: на входе в такт очищается, поэтому правки мимо методов между тактами (тесты, другие
   процессы, `scripts/lab`) видны со следующего такта. `get` каждый раз отдаёт новый объект (кэшируется
   текст JSON) — изменение результата модулем кэш не портит. `set` того же значения внутри такта — без записи.
2. **Один коммит на такт**: внутри такта `Memory._commit()` откладывает коммит до выхода из такта (`finally`
   — и при исключении). Вызов LLM (`decide`) вынесен из такта (`step_rules()` + `decide` под lock, порядок
   проверок тот же), поэтому записи не висят незакоммиченными на время ответа модели. Вне такта (скрипты,
   отчёты, `lab`) — коммит сразу, как раньше; `close()` коммитит отложенное.
3. **Снимок тела без лишней записи**: `mem.set_changed("last_state", …)` — тот же снимок (тело стоит в
   городе, спит) не пишется повторно. Содержимое БД то же.
4. **Индекс для count_events** (миграция схемы памяти v3 с копией `memory.sqlite.bak-v2`, как AUT-107):
   частичный индекс `events_kind_ts ON events(kind, ts) WHERE length(kind) >= 0`. SQLite берёт частичный
   индекс, только если в запросе есть тот же терм, — его добавляет лишь `count_events`. Остальные запросы к
   `events` (курсоры `id > ? AND kind IN (…) ORDER BY id`, выборки по `ts` без ORDER BY) идут прежними
   планами, порядок их строк не меняется (проверяет `tests/test_perf.py`). count_events «kill за неделю» на
   38 тыс. событий: 2.6 мс → 0.2 мс.
5. **TICK_EVERY в реестре** (`modules.py`): модуль объявляет период тика; если у экземпляра есть свой
   `next_tick` (первая строка tick — `if now < self.next_tick: return`), реестр не зовёт tick до этого срока
   (часы — `module.clock`), сброс `next_tick = 0` работает как раньше; иначе срок ведёт реестр. Поставлен
   модулям, которые уже троттлили себя сами: aims, bestiary, collection, dream, episodes, memoir, mentor,
   rivalry, rumors, savings (gossip — нет: до проверки срока шлёт очередь сплетен). Выигрыш по времени мал
   (вызовы и так выходили сразу), смысл — единый объявленный контракт, который проверяет тест-страж.
6. **memoir**: `item_label` звал `Prices.load()` на каждую строку мемуаров — пересборка словаря цен
   (≈ 3 мс) тысячи раз, недельная сборка мемуаров занимала ~1 с под профайлером. Справочник теперь один на процесс.

## 5. Что сознательно НЕ сделано

- **Полный индекс `events(kind, ts)`** — проверен и отклонён: SQLite начинает брать его для курсоров
  `id > ? AND kind IN (…) ORDER BY id` (society, collection, episodes, gossip, шина) вместо диапазона rowid —
  0.01 мс → 0.24 мс на каждый тик; запросы без ORDER BY (`ts >= ? AND kind IN …`: economy.metrics, mood)
  начали бы отдавать строки в другом порядке. Отсюда частичный индекс только для count_events.
- **Кэш count_events на тик** — в бою `since = time.time() - N` разный при каждом вызове, кэш не попадает;
  после индекса count_events дешёвый.
- **Троттлинг модулей, реагирующих на тело каждую секунду** (routine, party, crew, social, activities…) —
  это изменение поведения (реакция на смерть/тревогу/сделку позже на N секунд). Не трогал.
- **Отложенный коммит между тактами** (снимок тела + следующий step одним коммитом) — ещё ~ −0.2 коммита/тик,
  но записи висели бы незакоммиченными, пока тело отключено (`run` не зовёт step). Не стал.

## 6. Тест-страж

`tests/test_perf.py` (≈ 1 с):
- `SteadyStateBudgetTest` — настоящий Mind, сценарий day, 20 мин игрового времени после 5 мин прогрева:
  в среднем ≤ **20 SQL** и ≤ **1 коммита** на тик; ни один модуль не делает больше **4 запросов** за тик;
  каждый модуль с `TICK_EVERY` вызван не чаще `секунд / TICK_EVERY + 1` раз. На коде до perf тест падает
  (29.8 SQL/тик; party 10, routine 6).
- `RegistryTickEveryTest` — реестр: модуль без TICK_EVERY тикает каждый такт, с TICK_EVERY — раз в N с,
  свой `next_tick` уважается, его сброс даёт тик в следующем такте.
- `TickCacheTest` — кэш такта сквозной (set/get, отношения, изменение результата, правка мимо методов между
  тактами), один коммит на такт и видимость другим соединениям после такта, `set_changed`, кэш активного
  плана, частичный индекс только у count_events.

Время на тик тест не проверяет (зависит от машины) — для него `tools/profile_step.py`.

**Новый модуль**: тест упал — `python3 tools/profile_step.py --statements 20` покажет запрос, который
повторяется каждый тик. Читать kv/отношения через `mind.mem` (кэш такта), тяжёлое — раз в N секунд
(`TICK_EVERY` или свой `next_tick`), поток событий — по курсору `id`, «сколько событий вида за период» —
`mem.count_events` (индекс), а не свой `SELECT … WHERE kind = ? AND ts >= ?`.

## 7. Риски

- **Миграция схемы памяти v3** (индекс): при первом старте после обновления — копия
  `memory.sqlite.bak-v2` и построение индекса (на 40 тыс. событий — десятки мс). Данные не меняются. Откат кода
  на v2 работает с файлом v3 (лишний индекс не мешает; `migrate` при version ≥ SCHEMA_VERSION ничего не делает).
  Если параллельно кто-то тоже поднимет `SCHEMA_VERSION` — согласовать номер.
- **Коммит в конце такта**: при падении процесса посреди такта теряются записи этого такта (≤ 1 с), раньше —
  только записи после последнего коммита. При `kill -9` разницы почти нет (WAL + synchronous=NORMAL и так
  не гарантирует последние транзакции при потере питания).
- **Кэш такта** не видит запись в `kv`/`relations`/`plans` мимо методов `Memory`/`PlanStore` **внутри**
  того же такта. В коде мозга таких записей нет (проверено grep); новый модуль должен писать через методы.
- `TICK_EVERY` с собственным `next_tick`: реестр и модуль читают часы в разные моменты (микросекунды) —
  на границе срока тик может случиться на такт позже. В реплее (часы стоят) — точно как раньше.
- Замер синтетический: на VPS иная нагрузка (реальная шина нескольких жителей, LLM). Повторить
  `tools/profile_step.py --history 14` на VPS с разрешения владельца.
