# CHECKS — самопроверка ИИ после каждого шага

Нумерация шагов та же, что в STEPS.md. У каждого шага есть автоматическая проверка: ИИ-исполнитель сам запускает её, сохраняет доказательства и идёт дальше только при PASS. Ты смотришь всё вместе в конце вехи: 10–15 минут по списку «Смотр вехи».

## Как этим пользоваться

1. Отдаёшь ИИ этот файл вместе с STEPS.md, IMPLEMENTATION_BRIEF.md, ARCHITECTURE.md и промптом ниже.
2. ИИ проходит шаги вехи подряд. После каждого шага запускает `checks/NN.sh`. Если PASS — берётся за следующий, если FAIL — останавливается и пишет отчёт.
3. В конце вехи ИИ ждёт тебя. Ты читаешь `PROGRESS.md`, открываешь папку `evidence/` и делаешь смотр вехи в игре.

**Чего ИИ сам проверить не может** (это остаётся тебе на смотре вехи): как всё выглядит в клиенте, слышен ли голос, звучит ли речь «в характере», нравится ли тебе результат. Всё остальное проверяется по базе сервера, журналам и процессам.

## Промпт для ИИ (скопировать)

```
Ты реализуешь проект «живые жители RO» строго по шагам из STEPS.md, веха <БУКВА>, шаги <N–M>.
Архитектура — ARCHITECTURE.md, детали первых вех — IMPLEMENTATION_BRIEF.md, проверки — CHECKS.md.
Для каждого шага по порядку:
1) Сначала напиши проверку checks/NN.sh по описанию в CHECKS.md и запусти её. Она должна дать FAIL,
   потому что функции ещё нет. Сохрани вывод в evidence/NN/before.txt.
2) Реализуй шаг. Делай только то, что описано в этом шаге, — ничего из будущих шагов.
3) Запусти checks/NN.sh. PASS — допиши в PROGRESS.md: шаг, дата, PASS, что сделано, путь к evidence. Переходи к следующему шагу.
4) FAIL — до двух попыток исправить КОД (не проверку). Если не прошло — СТОП: запиши в PROGRESS.md,
   что не работает, что пробовал и какая гипотеза, и больше ничего не делай.
Запрещено: менять порог проверки; считать доказательством логи своего кода или чтение своего кода;
GM-команды и SQL-записи над жителями; обновлять rAthena/OpenKore/PACKETVER; выполнять шаги после
конца вехи. После последнего шага вехи — СТОП и сводка для владельца.
```

## Правила самопроверки: чтобы ИИ не обманул сам себя

1. **Проверка пишется до кода** и сначала обязана упасть (`before.txt`). Проверка, которая проходит до реализации, ничего не проверяет.
2. **Доказательства только внешние:**
   - база сервера: `residents.resident_events`, `picklog`, `zenylog`, `chatlog`, `char`, `party`;
   - список процессов, контрольные суммы файлов, вывод CLI-команд.

   Строки лога собственного плагина или оркестратора допускаются только **в паре** с внешним подтверждением.
3. **Проверку после первого запуска не правят.** Исключение — ошибка в самой проверке. Тогда в `PROGRESS.md` записывается причина и diff, а пороги не снижаются никогда.
4. **На каждый запуск — папка `evidence/NN/`:** полный вывод проверки, SQL-выборки, хеши, время начала и конца. Последняя строка вывода — ровно `RESULT: PASS` или `RESULT: FAIL: <причина>`.
5. **Тестер вместо тебя.** Где по шагу «ты что-то делаешь в игре», это делает персонаж-тестер под OpenKore (шаг 1б). Над тестером GM-команды разрешены, над жителями — никогда.
6. **Каждые 5 шагов — полный регресс:** все проверки предыдущих шагов вехи подряд. Если старое сломалось — СТОП.

## Общие инструменты

Они появляются по ходу шагов вехи A и дальше используются во всех проверках.

- `tools/tester.sh "<команда OpenKore>"` — отправить команду тестеру (шаг 1б);
- `tools/events.py --char <name> --since <ts> [--kind K]` — выборка событий свидетеля (шаг 6);
- `tools/wait_event.py --char <name> --kind <K> [--map M] --timeout <с>` — ждать событие, код выхода 0 или 1 (шаг 6);
- `tools/sql.sh "<SELECT …>"` — только SELECT, под пользователем `residents_ro` (шаг 4);
- `residents …` — CLI оркестратора (шаг 14 и дальше).
