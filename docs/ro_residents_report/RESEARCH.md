## 1. Neuro-Skyrim-Integration (NSI)

**Что это.** SKSE-плагин на C++, около 115 тыс. строк в `src/`, через который LLM управляет персонажем игрока в Skyrim. Связь с моделью идёт по Neuro API (WebSocket). Сама модель внешняя: Gary, Jippity, Tony или Randy (`docs/Testing.md`) **[Ф]**. Слова README: «Skyrim mod that can allow an LLM to play the game using text inputs» **[Ф]**.

### 1.1 Ответы на вопросы раздела 1

**Как агент получает достоверное состояние мира.**

- **[Ф]** Плагин работает внутри процесса игры и читает движок напрямую через CommonLibSSE. Пример: в `src/Socket.cpp:712-727` берутся `RE::PlayerCharacter::GetSingleton()`, `ControlMap` (можно ли ходить, смотреть, драться) и стадия квеста `MQ101`.
- **[Ф]** Окружение подаётся модели нумерованным списком объектов `objects_around` с флагом валидности (`src/Misc.cpp:24398-24480`). Модель ссылается на объект по `id` из этого списка.
- **[В]** Протокольного слоя между «телом» и состоянием здесь нет, поэтому рассинхронизации «клиент думает одно, сервер другое» тоже нет. В RO так не получится: внешний бот видит мир через сетевые пакеты.

**Какие события запускают решение модели.**

- **[Ф]** Наблюдатель `Observer.cpp` (9 701 строка) шлёт контекстные сообщения о событиях: «You see: …», «You hear something…», ошибки. Только в этом файле около 120 вызовов `send_random_context`.
- **[Ф]** «Тычки» при бездействии. Если модель молчит, а исполнитель простаивает, через случайные 6–10 с отправляется фраза вроде «[Choose next action to do]» (`src/Socket.cpp:1153-1302`, `time_threshold = rand*4 + 6`).
- **[Ф]** Принудительный выбор (`actions/force`) для меню: строки диалога, торговля, взлом, повышение уровня, перки (`src/Socket.cpp:1368-1454`, `switch (get_active_force())`).
- **[В]** Модель здесь опрашивается каждые несколько секунд. Для одного стримерского персонажа это нормально. Для 20 жителей на внешнем API такая частота неприемлема.

**Как устроены действия и их динамические ограничения.**

- **[Ф]** В `src/Socket.hpp` (namespace `Capabilities`) объявлено 44 действия: `walk_to_object`, `attack_object`, `use_inventory_item`, `go_to_location`, `tactical_retreat` и другие. Параметр почти всегда один: `id` из перечисленного списка (`NeuroChoiceJson`).
- **[Ф]** Набор зарегистрированных действий пересчитывается по состоянию (`register_allowed_actions`, `src/Socket.cpp:697-1018`). Учитываются `can_walk`, `can_fight`, бой, нахождение в поселении, скрытность, облик вампира, тюрьма и стадия вступительного квеста.
- **[Ф]** У действий есть кулдауны авторегистрации (`src/Socket.cpp:1306-1317`). Есть сторожа: через 30 и 120 с без зарегистрированных действий набор регистрируется заново, а ходок сбрасывается (`src/Socket.cpp:1031-1081`).
- **[В]** Это главная переносимая идея: модель видит только те глаголы, которые сейчас выполнимы, а объекты выбирает из списка, подготовленного исполнителем.

**Где заканчивается LLM и начинается исполнитель.**

- **[Ф]** Модель выбирает глагол и `id`. Всё остальное делает детерминированный код. `WalkerProcessor.cpp` занимает 26 841 строку: пути, обход застреваний, двери, бой, тайминги. `Misc.cpp` — 37 052 строки.
- **[В]** Соотношение показательное: интеграция «LLM играет» на 95% состоит из исполнителя и лишь на 5% из протокола модели.

**Навигация, бой, диалоги, инвентарь, обслуживание.**

- **[Ф]** Навигация. Свой ходок с заранее заданными путями (`CustomWalkerPaths.hpp`, 988 строк), запоминанием места застревания и попытками выбраться (`WalkerProcessor.cpp:813-849, 1876-1878`).
- **[Ф]** Бой: `attack_object` → `walk_to_object_by_index(id, 3)` (`Socket.cpp:2052-2059`).
- **[Ф]** Диалоги с NPC — это выбор готовой строки из ванильного меню через force (`DialogueProcessor.cpp`). LLM-реплик NPC в NSI нет.
- **[Ф]** Инвентарь и торговля — отдельные процессоры: `BarterProcessor.cpp` (5 349 строк), `ContainerProcessor.cpp` и другие.
- **[Ф]** Много контентно-специфичных подсказок под конкретные formID и головоломки (например, `Observer.cpp:4221`, `WalkerProcessor.cpp:18274`).

**Как определяются успех, отказ, зависание и перепланирование.**

- **[Ф]** Результат действия по Neuro API означает результат *проверки*, а не исполнения. В спецификации: «This message needs to be sent as soon as possible after an action is validated» (`neuro-sdk/API/SPECIFICATION.md:164-192`). Рекомендации усиливают это: «Send the result as soon as you have validated the action, before executing it in-game» (`API/BEST_PRACTICES.md`, раздел Action Results).
- **[Ф]** Отказ возвращается с объяснением для модели. Пример: `walk_to_object_by_index` отдаёт `{false, "You cannot walk yet"}` (`WalkerProcessor.cpp:9566-9615`).
- **[Ф]** Завершение или провал в игре приходят позже, отдельным контекстом. Зависание ловит ходок (stuck), а сторож регистрации сбрасывает ходока.
- **[В]** Перепланирования как механизма нет. Модель просто делает следующий выбор после «тычка».

**Что сохраняется между сессиями.**

- **[Ф]** Плагин хранит только настройки (`_neuroSkyrim.ini`, `Misc.cpp:28579`). Игра сохраняется штатно.
- **[Ф]** Память модели живёт в бэкенде Neuro API: «Context survives disconnects» (`BEST_PRACTICES.md`). Своей памяти, отношений и целей в NSI нет.

**Есть ли самостоятельные NPC, отношения и долговременные цели.**

- **[Ф]** Нет. Управляется только персонаж игрока. Долговременные цели — это квесты, по которым модель идёт действием `follow_quest`.

**Как связаны STT, ответ, TTS и действия.**

- **[Ф]** В самом моде речи нет. В Neuro API есть сообщение `speech_finished` (`SPECIFICATION.md:242-262`) и необязательный голосовой side-channel. Там же сказано: «Voice is a conversational side channel; gameplay must never depend on Neuro responding vocally» (`API/VOICE_CHAT.md`).

**Что переносимо в RO, а что специфично для Skyrim.**

| Механизм | Переносимость в RO |
|---|---|
| Набор действий зависит от состояния | **Да.** Перенести в оркестратор как список «доступных занятий/навыков» |
| Параметр — `id` из списка, подготовленного исполнителем | **Да.** Карты, точки, жители и предметы задаются только из списков |
| Проверка → немедленный результат с понятной причиной; завершение — отдельным событием | **Да**, и дополнить подтверждением со стороны сервера |
| Сторожа «ничего не зарегистрировано» и «исполнитель застрял» | **Да** |
| Частые «тычки» каждые 6–10 с | **Нет.** Слишком дорого для множества жителей |
| Чтение памяти движка изнутри процесса | **Нет.** В RO его заменяет серверный свидетель (см. §8) |
| Принудительный выбор для UI-меню | Частично: диалоги NPC в RO лучше делать заскриптованными навыками |
| Контентные подсказки под конкретные объекты | Специфично для Skyrim |

## 2. Neuro API как образец контракта действий

- **[Ф]** Сообщения: `startup`, `context {message, silent}`, `actions/register`, `actions/unregister`, `actions/force {state, query, ephemeral_context, priority, action_names}`, `action/result {id, success, message}`; входящие — `action`, `speech_finished` (`SPECIFICATION.md`).
- **[Ф]** При `success:false` внутри force действие повторяется автоматически. Поэтому неудачу, которую не нужно повторять, рекомендуют отдавать как `success:true` с сообщением об ошибке (`SPECIFICATION.md:188-192`).
- **[Ф]** Если результата нет примерно 20 с, сервер сам считает действие неудачным. Набор действий рекомендуют держать стабильным: «avoid rapidly registering and unregistering actions» (`BEST_PRACTICES.md`).
- **[В]** Для жителей RO берём эту двухуровневую семантику, но называем уровни явно: `accepted|rejected` (проверка) и `confirmed|failed|timed_out|cancelled|unknown` (итог по свидетельству игры). Смешение «принято» и «сделано» — одна из корневых ошибок live_ro (§5).

## 3. Mantella

**Что это.** Python-сервер (FastAPI). Мод Skyrim или Fallout 4 опрашивает его по HTTP, и сервер ведёт голосовые разговоры с NPC: STT → LLM → TTS **[Ф]** (`README.md`, `src/http/routes/mantella_route.py`).

### 3.1 Ответы на вопросы

- **Состояние.** **[Ф]** Мод игры присылает JSON: участники, локация, время, погода, ближайшие актёры, события в игре (`src/http/communication_constants.py`, ключи `KEY_CONTEXT_*`, `KEY_ACTOR_*`). Python память игры не читает.
- **Триггеры.** **[Ф]** Цикл задаёт игра (pull): `initialize`, `start_conversation`, `continue_conversation`, `player_input`, `end_conversation` (`mantella_route.py:83-93`). Разговор начинает игрок. «Радиантные» разговоры NPC↔NPC запускает мод игры.
- **Действия.** **[Ф]** Действия описаны в JSON (`data/actions/*.json`, `data/actions/functions/*.json`: follow, attack, loot_items, move_npc, use_item, wait_npc…) и отдаются LLM как инструменты. Аргументы проверяются по схеме (`src/actions/function_manager.py:18-60`). У части действий стоит флаг `requires_response`: игра должна сообщить результат (`function_manager.py:238, 344-372`; `game_manager.py:145-152`).
- **Граница LLM.** **[Ф]** LLM порождает речь и выбирает инструмент. Исполняет игра своим AI-пакетом NPC. Навигацию и бой Mantella не реализует.
- **Успех и отказ.** **[Ф]** Результат возвращается только для действий с `requires_response`, остальные исполняются по принципу «отправил и забыл». Конец разговора наступает через `should_end`, инструмент EndConversation или лимит ходов радиантного диалога `radiant_max_turns` (`src/conversation/conversation_type.py:136-156`; `src/config/definitions/prompt_definitions.py:358-363`).
- **Память.** **[Ф]** По каждому NPC в каждом мире хранятся сводки разговоров в файлах. При переполнении делается сводка сводок (`src/remember/summaries.py:64-91, 230-320`).
- **Самостоятельные NPC.** **[Ф]** Нет. Радиантные диалоги — это короткие сессии речи между соседними NPC с лимитом ходов. Целей, распорядка и отношений сверх сводок и игрового `relationship rank` нет.
- **STT → LLM → TTS → игра.** **[Ф]** Цепочка такая:
  - STT: Moonshine или Whisper, есть push-to-talk;
  - потоковый ответ LLM нарезается на предложения;
  - TTS на каждое предложение: Piper, xVASynth, XTTS или OpenAI-совместимый;
  - на выходе файлы wav, `.lip` и `.fuz` для липсинка Skyrim (`src/tts/ttsable.py:37-140`);
  - следующая реплика ждёт `voice_line_duration`;
  - игрок может перебить голосом, тогда генерация останавливается (`src/conversation/conversation.py:129-225`).
- **Переносимо в RO:**
  - модель «сессия разговора» с лимитом ходов и явным концом;
  - потоковая нарезка на предложения;
  - пейсинг по длительности фразы;
  - перебивание;
  - сводки памяти по персонажу;
  - проверка вызовов инструментов по схеме.
- **Специфично для Skyrim и Fallout:** `.lip`/`.fuz`, voice types и главное — **игра сама проигрывает произвольный wav с диска**. Стандартный клиент RO так не умеет (§9).

## 4. Mindcraft (дополнительный референс: LLM-боты в Minecraft поверх mineflayer)

Mindcraft выбран потому, что это прямой аналог схемы live_ro: LLM-мозг плюс готовое «тело»-клиент.

- **[Ф]** Слой быстрых реакций `modes` работает без LLM. Режимы упорядочены по приоритету: `self_preservation` прерывает всё, затем `unstuck`, `cowardice`, `self_defense`, `hunting`, `item_collecting` и другие. Комментарий в коде: «a mode is a function that is called every tick to respond immediately to the world… the order of this list matters» (`src/agent/modes.js:13-26, 91-297`).
- **[Ф]** Менеджер действий задаёт таймаут (10 с по умолчанию) и принудительно останавливает процесс, если код не отпускает управление 10 с (`src/agent/action_manager.js:18-61`).
- **[Ф]** Менеджер разговоров между ботами: один активный разговор, ответ «I'm talking to someone else, try again later» с `!endConversation`, таймаут, если собеседника нет в игре (`src/agent/conversation.js:50-253`).
- **[Ф]** Генерация и исполнение кода моделью по умолчанию выключены: `"allow_insecure_coding": false // allows newAction … model can write/run code on your computer` (`settings.js:43`). Для нас это анти-образец: модель не пишет и не исполняет код.

- Настоящая сделка: 3 зелья от Arkady к Vera, завершение подтверждено сервером (`HERMES-service-trade-fix.md`).
- Лечение Arkady на 282 и 237 HP «ранее в городе» (там же).

Не подтверждено ни разу: полный суточный цикл, совместная охота, устойчивая автономия, сбор пятерых.

### 5.3 Причины ненадёжности: свидетельства и уверенность

Сначала главное: **виновата не модель**. LLM в live_ro по умолчанию выключена (`BRAIN_LLM=off`), а почти все провалы относятся к исполнителю, состоянию и процессу разработки.

#### П1. Объём кода обогнал проверку. Уверенность: высокая

- **[Ф]** С 17:30 02.10 до 00:35 03.10 (UTC) добавлены модули слухов (`rumors.py`, 17:32), гильдии (19:54), соперничества и погоды (20:11–20:13), сплетен (21:27), мечты (`dream.py`, 21:33), наставничества (22:05), спарринга (23:06), свадеб (`wed.py`, 23:45), праздников (`fest.py`, 23:53), «бюджета внимания» (`attention.py`, 00:35) и других: всё это появилось, пока по базовым заданиям №7 и №8 (доставка, группа, встреча) не было ни одного runtime-отчёта (`STATUS.md:50-55`, статус «⏳»).
- **[Д]** Сводка 59 «код» против 3 «VPS» (`AUTONOMY_STATUS.md:13`) и красные Python-тесты (`HERMES-service-trade-fix.md`).
- **[В]** Это главный корень. Каждый модуль добавлял владельца тела, метки протокола и поля промпта. Число стыков росло быстрее, чем их успевали проверить. Сами метки «ревизий стыков» в комментариях кода (`review2`, `review3`, `review4` в `lifecycle.py` и `mind.py`) и коммит «Ревизия стыков модулей» (`f2042fd`) показывают, что стыки ломались ещё до игры.

#### П2. Намерение фиксировалось вместо результата. Уверенность: высокая

- **[Ф]** Плагин отвечает `ack ok`, как только команда OpenKore *запущена*: `Commands::run(...)` и сразу `sendMsg({type => 'ack', ... ok => ...})` (`bots/plugins/brainBridge/brainBridge.pl:1086-1104`). Мозг пишет в журнал «исполнено в игре» по этому ack (`brain/live_brain/mind.py:402-407`).
- **[Д]** Hermes нашёл реальный провал: «Ack сам по себе недостаточен: до исправления ignoreAll тоже был ack, хотя сервер отвергал сообщения» (`HERMES-LIVE-JEV.md`).
- **[Ф]** Подтверждение сервером (`delivery`) добавили только для `say` и `whisper` (`brainBridge.pl:453-493`). Остальные действия (`hunt`, `meet_point`, `follow`, `service` …) подтверждаются лишь косвенно, по следующему снимку состояния.
- **[Ф]** Многие «действия» — это записи в конфиг OpenKore: `conf lockMap`, `conf lockMap_x` и так далее (`brainBridge.pl:651-701`). Результат такого действия — «настройка изменена». Дошло ли тело, мозг потом выводит из позиции.

#### П3. Мозг конкурировал со встроенной автоматикой OpenKore. Уверенность: высокая

- **[Ф]** Тело — полный автомат OpenKore: `attackAuto 2`, `route_randomWalk 1`, `sellAuto`, `buyAuto`, `storageAuto`, `partyAuto 1`, `itemsTakeAuto`, `sitAuto_idle 1` (`bots/bot01/control/config.txt:71-308`). Мозг управлял им, переставляя те же ключи из многих модулей: распорядок, план встречи, экономика, группа, экспедиции, дом, травник. Отсюда понадобился арбитр «survival > plan > economy > party > routine» (`brain/live_brain/lifecycle.py:19-23, 33, 123-146`). Встроенные циклы OpenKore (закупка, склад, случайная ходьба, атака) в этот арбитр не входят.
- **[Ф]** В комментариях кода зафиксированы найденные конфликты:
  - команда `sit` ставит `sitAuto_forcedBySitCommand`, и OpenKore «перестаёт продавать, ходить к lockMap и атаковать» (`brainBridge.pl:715-719, 626-630`);
  - `ai manual` отключает самооборону, зелья и респаун (`brainBridge.pl:19-21`);
  - `partyAuto` успевает отказать в приглашении раньше мозга, поэтому приём перенесли в хук плагина (`brainBridge.pl:102-104, 401-412`);
  - в чат-комнате сервер не даёт ходить (`brainBridge.pl:544-569`).
- **[Д]** Цикл закупки и склада зацикливался. Магазин отдаёт корейское имя `빨간포션`, а OpenKore ищет по английскому, поэтому считал запас нулевым (`HERMES-579b0ef.md`).
- **[Д]** «A rest command sent immediately after process launch, before fresh state, did not yield the expected town mode» (`HERMES-cbeb2a9.md`).

#### П4. Состояние, план и память расходились. Уверенность: средняя–высокая

- **[Ф]** Позиция в состоянии — это `pos_to`, то есть *цель* текущего шага движения, а не текущая клетка (`brainBridge.pl:235, 334, 351, 449, 704`). OpenKore вычисляет текущую позицию интерполяцией: `Utils::calcPosition` (`openkore/src/Utils.pm:763-785`).
- **[Д]** Из-за этого сделка предлагалась «до фактического приближения». Исправлено только в плагине economy (`HERMES-service-trade-fix.md`; `bots/plugins/economy/economy.pl:172`). В `brainBridge` осталось `pos_to`, а на нём построены проверки «дошёл» и «встретились» в `plans.py` (`brain/live_brain/plans.py:138-153`).
- **[Ф]** Состояние приходит раз в 15 с (`brainBridge_stateInterval`, по умолчанию 15; `brainBridge.pl:1147`). Свежим считается снимок до 60 с (`lifecycle.py:28`, `STALE_SEC = 60`).
- **[Ф]** Каждая команда `conf` записывает `config.txt` на диск: `configModify → saveConfigFile()` (`openkore/src/Misc.pm:509-571`). Значит, решения мозга становятся «профилем» тела и переживают перезапуск, хотя план в мозге мог уже завершиться. В архиве у bot01 зафиксировано `lockMap orcsdun01`, и из репозитория нельзя понять, кто это записал: оператор или мозг (`git show 38208c1 -- bots/bot01/control/config.txt`).
- **[Д]** «the live body can hunt while its last prose goal still says it waits in town» (`HERMES-cbeb2a9.md`, пункт 5 follow-ups). Arkady однажды назвал Vera мужчиной (`HERMES-LIVE-JEV.md`).

#### П5. Ошибки, повторы и идемпотентность. Уверенность: средняя

- **[Ф]** Идентификатор действия — счётчик внутри процесса мозга с 1 (`brain/live_brain/bridge.py:16, 64-69`). При переподключении `self.sent.clear()` (`mind.py:503-517`). В плагине нет учёта уже исполненных `id` (`brainBridge.pl:1070-1105`), то есть защиты от повторной доставки нет.
- **[Ф]** Незавершённая передача `giving` хранится только в памяти мозга (`brain/live_brain/economy.py:102, 342-371`).
- **[В]** Это создаёт окно для расхождения «мозг считает неудачей, сервер — сделкой» и, при повторе запроса, для двойной передачи. Runtime-случаев двойной передачи в отчётах нет.
- **[Ф]** Хорошее решение в этой части: ответ модели отбрасывается, если за время раздумья сменились эпоха, смерть, карта, режим или план (`mind.py:842-857`).

#### П6. Зависимость от ручных вмешательств. Уверенность: высокая

Все пункты — **[Д]**:

- Arkady был мёртв в Payon Dungeon. Респаун по просьбе владельца оставил его почти без HP и с перегрузом больше 70%. Лечили вручную, через восемь и две команды зелий (`HERMES-cbeb2a9.md`, раздел «Owner-requested revival»).

- Режим «оставить обоих в городе» выбирал оператор (`HERMES-service-trade-fix.md`).
- Сам цикл проверки целиком зависел от оператора-агента.

#### П7. Маршруты, снабжение и координация. Уверенность: средняя

- **[Ф]** Таблицы порталов генерировались под renewal (`scripts/gen_portals.py`, `okroute.py`). Встреча и группа зависели от шёпотов с машинными метками `[meet:…]` и `[party:…]` (`plans.py:1-25`, `party.py:28`), то есть от доставки личных сообщений.

## 6. OpenKore: что важно для исполнителя

- **[Ф]** Перемещение можно ставить задачей с отслеживаемым итогом. `Actor::route(map, x, y, %args)` создаёт `Task::MapRoute` или `Task::Route` с `maxTime`, `distFromGoal`, `notifyUponArrival` и кладёт в очередь AI (`src/Actor.pm:838-867`). У задачи есть статусы `INACTIVE/RUNNING/STOPPED/DONE` (`src/Task.pm:72-99`) и коды ошибок `TOO_MUCH_TIME`, `CANNOT_CALCULATE_ROUTE`, `STUCK`, `UNEXPECTED_STATE` (`src/Task/Route.pm:44-58, 229, 315, 471, 523`). Есть хук `route` со статусами `success` и `stuck` (`Task/Route.pm:380-727`).
- **[Ф]** live_ro этим не пользовался: в плагинах нет ни `Task::*`, ни `TaskManager`, только `Commands::run` и `conf` (`grep` по `bots/plugins`).
- **[Ф]** `conf` сохраняет файл: `configModify` → `saveConfigFile()` (`src/Misc.pm:509-571`; `src/Commands.pm:2121-2180`).
- **[Ф]** Хуки для подтверждений: `self_died`, `target_died`, `item_gathered`, `packet_privMsg`, `packet_pre/private_message_sent`, `packet_selfChat`, `complete_deal`, `finalized_deal`, `party_invite`, `packet_skilluse`, `AI_sell_auto_completed`, `AI_buy_auto_completed`, `zeny_change` (использование в `brainBridge.pl:141-171`, `economy.pl:42-61`; список вызовов `callHook` в `src/Task/Route.pm`, `src/AI/CoreLogic.pm`, `src/Network/Receive.pm`).
- **[Ф]** Позиция: `pos` — начало отрезка, `pos_to` — его конец, текущая клетка считается через `calcPosition` (`src/Utils.pm:763-785`; `src/Actor.pm:215-233`).
- **[В]** OpenKore — зрелое «тело»: маршруты между картами, бой, подбор, NPC-магазины, склад. Брать его как исполнителя оправданно, если отслеживать *задачи*, а не переключать *настройки*.

## 7. rAthena: реальные возможности серверной основы

- **[Ф]** Сессии игроков без клиента в ядре есть только для автоторговцев. При старте сервер создаёт `map_session_data` с `fd = 0`, ставит `state.autotrade = 1|2` и аутентифицирует через `chrif_authreq(sd, true)` (`src/map/vending.cpp:593-650`; `src/map/chrif.cpp:627`). Это пассивные торговцы, а не играющие персонажи.
- **[Ф]** Команды скриптов для управления юнитами: `unitwalk`, `unitwalkto`, `unitattack`, `unitskilluseid`, `unitskillusepos`, `unitstopwalk`, `unittalk`, `unitwarp`, `getunitdata`/`setunitdata` (`doc/script_commands.txt:8700-8886`). Важное ограничение: `unitwalk` работает в пределах текущей карты — «there is no way to move across an entire map with 1 command use» (`script_commands.txt:8700-8712`). Межкартовых маршрутов нет.
- **[Ф]** `clone` создаёт **монстра**-копию игрока («This command creates a monster which is a copy of another player», `script_commands.txt:7067-7090`). Инвентаря, группы и опыта как у игрока у клона нет.
- **[Ф]** Скриптовые события с привязкой к игроку: `OnPCLoginEvent`, `OnPCLogoutEvent`, `OnPCDieEvent` (с `killerrid`), `OnNPCKillEvent` (с `killedrid` и `killedgid`), `OnPCBaseLvUpEvent`, `OnPCJobLvUpEvent`, `OnPCLoadMapEvent` (нужен mapflag `loadevent`), `OnWhisperGlobal` (`script_commands.txt:990-1030`; `src/map/script.cpp:263-279`).
- **[Ф]** Серверные журналы в SQL (`conf/log_athena.conf`):
  - `picklog` — по типам: T сделки, V лавки, P подбор/выброс, S покупка и продажа у NPC, C расход, R склад, E почта, B скупка, K банк и другие; есть `unique_id` предмета;
  - `zenylog`;
  - `chatlog` с битами global, whisper, party, guild (`src/map/log.hpp:16-26`).
  - Запись идёт синхронно при событии (`src/map/log.cpp:207-258`). Для InnoDB — `INSERT`, для MyISAM — `INSERT DELAYED` (`log.cpp:49-55`).
  - По умолчанию `enable_logs: 0xFFFFFFFF`, `log_filter: 1`, но `log_zeny: 0` и `log_chat: 0` выключены.
- **[Ф]** Персонаж сохраняется раз в `autosave_time: 300` с, а также после сделки, лавки, закрытия склада и почты (`conf/map_athena.conf:87-105`; `trade.cpp:683-684`, `storage.cpp:479, 503`). Значит, таблицы `char` и `inventory` годятся как поздняя сверка, но не как «живой» источник.
- **[Ф]** Звук: `soundeffect` и `soundeffectall` проигрывают **только wav, который уже есть в GRF клиента** («Effect filename is the filename in a GRF», `script_commands.txt:8430-8445`). У «плавающего» NPC звук центрируется на прикреплённом персонаже (там же). `playBGM` проигрывает mp3 из папки `/BGM/` клиента (`script_commands.txt:8457-8470`).
- **[Ф]** Системы плагинов (как HPM у Hercules) в rAthena нет. Изменения ядра — это fork и патчи (так же рассуждает `live_ro/docs/SUBMODULES.md` **[Д]**).

## 8. Сравнение основ для RO

Варианты:

- **A.** Внешние игроки-боты OpenKore, мозг управляет через конфиг (как в live_ro).
- **B.** Серверные управляемые персонажи rAthena: собственный модуль C++, сессии без клиента по образцу автоторговцев и контроллер поведения.
- **C.** Гибрид: OpenKore-исполнитель с отслеживаемыми задачами, серверный «свидетель» rAthena (скриптовые события и SQL-журналы, только чтение для оркестратора) и единый оркестратор.
- **D.** NPC-«статисты»: NPC со спрайтом профессии, ходят и говорят скриптом.

| Критерий | A: OpenKore как в live_ro | B: серверные персонажи | C: гибрид | D: NPC-статисты |
|---|---|---|---|---|
| Полнота игровых возможностей | Полная: обычный игрок | Только то, что напишем; NPC-диалоги, магазины и респаун без клиента придётся вызывать в обход `clif_parse_*` **[В]** | Полная (как A) | Нет инвентаря, группы, опыта, боя как у игрока |
| Достоверность состояния | Низкая–средняя: взгляд клиента, `pos_to`, снимок раз в 15 с | Высокая (сервер) | Высокая для ключевых фактов: сервер подтверждает, тело даёт детали | Высокая, но нечего подтверждать |
| Навигация и действия | Зрелые в OpenKore | Межкартовую навигацию писать с нуля (`unitwalk` в пределах карты) | Зрелые, плюс итог задачи | `npcwalkto` в пределах карты |
| Видимость в обычном клиенте | Да | Да (как автоторговцы) **[В]** | Да | Да, но как NPC |
| Сложность разработки | Низкая на старте, высокая в сопровождении (П3) | Очень высокая: C++ ядро, fork rAthena | Средняя: плагин-исполнитель, скрипт-свидетель, оркестратор | Низкая |
| Нагрузка | Процесс OpenKore на жителя (RAM не измерена) | Минимальная на жителя **[В]** | Как A плюс малая нагрузка свидетеля | Минимальная |
| Зависимость от версий | PACKETVER ↔ serverType OpenKore | Сильная: fork ядра | PACKETVER (как A) и мягкая: скрипт и конфиг логов, ядро не трогается | Слабая |
| Риск обхода правил админ-средствами | Низкий, если нет GM-команд | **Высокий**: прямые вызовы `pc_*` минуют проверки клиента; риск падения map-server для всех | Низкий: свидетель только наблюдает | — |
| Годится для «жителей» | Да, но ненадёжно (П2–П4) | Да, в перспективе | **Да** | Нет: декорации, а не жители |

**Выбор.**

- **Основной — C (гибрид).** Тело остаётся полноценным игроком, видимым в обычном клиенте и подчиняющимся всем правилам сервера. Корни провалов закрываются структурно:
  - навыки работают через задачи OpenKore с явными кодами ошибок, а не через `conf` (П2, П3);
  - успех подтверждает сервер, а не ack тела (П2, П4);
  - один владелец тела — исполнитель навыков (П3);
  - идемпотентность и единый журнал (П5).
- **Запасной — B (серверные персонажи).** Включать только при одном из условий:
  - (1) исполнитель на OpenKore не проходит критерии этапа 2 после двух итераций исправлений;
  - (2) замер RAM показывает, что 20 тел OpenKore не помещаются в бюджет VPS.

  B дорог, но убирает целый слой: протокол и клиентскую эмуляцию. Начинать его стоит с прототипа «сессия без клиента ходит по одной карте и бьёт монстра» в форке, на копии БД.
- **D** допустим только как декорация, явно помеченная как NPC, и к «жителям» не относится.

Почему C — это «жители мира», а не только фарм:

- каждое социальное действие (встреча, группа, передача, помощь) подтверждается событием сервера, видимым и людям;
- обещания привязаны к записям договорённостей, у которых есть проверяемый итог;
- отношения меняются от подтверждённых событий, а не от болтовни.

## 9. Голос в RO: что возможно

- **[Ф]** Стандартный клиент проигрывает только звуки, которые уже есть в его данных (§7). Динамический TTS «в клиент» без расширения невозможен.
- **[В]** Варианты:
  1. **Банк заранее записанных реплик.** Короткие «барки» каждого жителя упаковываются в патч GRF. Проигрывает их серверный скрипт: житель шлёт шёпот служебному «плавающему» NPC (`OnWhisperGlobal`), тот вызывает `soundeffectall` вокруг прикреплённого персонажа. Это гипотеза: позиционирование и поведение при PACKETVER 20180620 нужно проверить в игре. Синтез TTS делается офлайн разрешённым голосом.
  2. **Внешнее приложение-компаньон** рядом с клиентом: оверлей или веб-страница. Подписывается на события речи оркестратора, фильтрует по близости к персонажу человека (позицию даёт свидетель), проигрывает потоковый TTS с подписью говорящего. Клиент не модифицируется.
  3. **Веб-клиент roBrowserLegacy.** В нём есть `src/Audio/SoundManager.js` и `src/Renderer/Entity/EntitySound.js` **[Ф]**, то есть точки, где можно привязать звук к сущности. Нужен свой форк и websocket-прокси.
  4. **Патч или инъекция в официальный клиент — не рекомендуется**: юридические риски и хрупкость.
- **[Ф]** Принцип из Neuro API: голос — необязательный side-channel, геймплей от него не зависит (`API/VOICE_CHAT.md`).
