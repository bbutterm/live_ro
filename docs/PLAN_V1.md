# План v1: новый мир, этапы

Основан на повторном аудите 12.10.2026. Каждую находку проверили скептик, критик и сверка в коде.
- Этап готов, только когда его критерий выполнен по свидетелю и `ro status`. Тесты — не результат.
- Порядок важен: следующий этап строится на предыдущем.

## Решения владельца (12.10)
1. Приёмку v1 проходим на **новом мире** (новый VPS, новички, без GM). Старый мир выключен.
2. `main` общий: в него вливают разные боты. Каждый перед push делает слияние и проверку (см. «Как вливать в main»).
3. Расширения (каталог действий Hermes в меню LLM, новые сценарии) — после приёмки v1. Код каталога влит и доступен оператору через CLI.
4. ТЗ: суточная приёмка — пассивная. Мир просто работает, итог считает `ro accept` (внесено в `TZ_AUTONOMY_V1.md`).

## Как вливать в main (для всех ботов)
```
git fetch origin
git merge origin/main          # без rebase и force-push; конфликт решаем слиянием
make check                     # зелёный; пропуски допустимы только у тестов стенда VPS
git push origin HEAD:main      # если push отклонён — снова fetch + merge + make check
```
- `config/world.yaml` — база нового мира (3 жителя). Настройки конкретного сервера (кто выключен, дуэт, персоны оператора) хранятся только в `/var/lib/ro-world/world.local.json` на этом сервере, не в git.
- Снимки «как есть» с сервера в `main` не пушить. Работа в процессе — в своей ветке.
- Каждое отступление от ТЗ — строка в `docs/DECISIONS.md`.

## Этап 1. main зелёный, один мир в git — СДЕЛАНО (12.10)
- **Чат всегда отвечает игроку.** Если LLM недоступна, ограничена или упёрлась в бюджет, игрок получает честную короткую фразу о текущем занятии. Повтор заменяется другой фразой, а не тишиной. Молчать можно только на реплики жителей.
- **«Мой план»** — это намерение модели. Оно живёт отдельно от жизненного цикла задачи и не стирается после первого шага.
- **Конфиг.** В git лежит база (3 жителя, персоны без ложного класса в `residents.yaml`). Есть серверный overlay `world.local.json`:
  - проверяется по белому списку ключей и схеме;
  - при ошибке берётся последняя верная копия, а причина видна в `ro status`.
- **Удалена ссылка `plugins/raiseSkill`** на файл вне репозитория.
- **Версия кода.** `ro status` первой строкой показывает, какой код запущен, и предупреждает, если checkout новее.
- **Тесты.** Устаревшие обновлены, 3 теста стенда VPS пропускаются вне VPS. `make check` зелёный.

**Осталось проверить вживую (на новом мире):** 4 реплики игрока за 2 минуты дают 4 ответа в `chatlog`, каждый не позже 10 с. В том числе при выключенной LLM: `llm.enabled=false` в overlay.

## Этап 2. Развёртывание нового мира и всё, что нужно до суточного прогона

**Статус на 12.10.** Код всех пунктов 2.1–2.10 сделан, `make check` зелёный. Проверено на стенде: настоящие rAthena, MariaDB и OpenKore на Ubuntu 24.04 в контейнере разработчика, а вместо LLM — локальная заглушка.
- **Развёртывание.** Одна команда поднимает мир за 9 минут, повторный запуск ничего не ломает.
- **Решения модели.** Модель выбирает занятия, и сервер их подтверждает (`walk_to`, `say`, `hunt`, `town_service` — `done`). За 15 минут у жителей 48–69 убийств, есть продажи и покупки.
- **Чат.** Ответ игроку приходит за 1 с, во время охоты, без её остановки. На шёпот житель отвечает шёпотом.
- **Follow.** «Пойдём со мной»: житель 102 из 103 замеров рядом по свидетелю. Гость без регистрации регистрируется и снимается.
- **Остановка мира.** После `ro stop/start` тот же процесс чата снова отвечает.
- **Порядок дальше.** Развернуть на сервере (`docs/DEPLOY_NEW_WORLD.md`) с настоящим ключом и пройти ворота этапа 2 по свидетелю.

Пункты 2.1–2.3 нужны до развёртывания или вместе с ним. Остальное — до этапа 3, в указанном порядке.

### 2.1 Часовой пояс БД — UTC с первого дня (S) — сделано в коде
- **Проблема.** Время свидетеля, чата и picklog разбирается как Europe/Amsterdam (`tools/events.py:30`, `packages/body_gateway/service.py:156`, `UNIX_TIMESTAMP` в `chat.ingest`). 25.10 с 01:00 до 02:00 UTC жители на час станут «офлайн», чат будет игнорировать игроков, подтверждения уйдут в timeout.
- **Как.**
  - Один ключ `db_timezone` в `config/world.yaml`: `"UTC"` для нового мира.
  - Все читатели берут зону из него.
  - В `DEPLOY_NEW_WORLD.md`: `timedatectl set-timezone UTC` и `default-time-zone='+00:00'` в MariaDB до первого запуска.
  - Тест: разбор DATETIME в обе стороны и окно 25.10.
- **Готово, когда:** `tools/events.py --follow` показывает `ts_utc`, совпадающий с `date -u` с точностью до секунд.

### 2.2 `ro doctor world` и `ro accept` — машинная приёмка (M) — сделано в коде
- **Проблема.** `ro doctor` проверяет только токен LLM. Критерии §1 ТЗ ни разу не принимались по свидетелю, доказательства есть только прозой.
- **Как.**
  - **`ro doctor world`, без LLM:**
    - службы `mariadb`, `ro-residents-*`, `ro-world`, `ro-chat` активны;
    - все жители из конфига включены и онлайн по свидетелю;
    - сокеты шлюзов отвечают;
    - версия кода;
    - свободное место на диске.
    Итог — PASS/FAIL по строкам.
  - **`ro accept --window 6h|24h`** читает `residents.resident_events`, `chatlog`, `decisions.jsonl` и `llm-spend.json` и выдаёт PASS/FAIL по каждому критерию §1:
    - аптайм каждого жителя;
    - не меньше 3 разных занятий по решениям LLM в каждом 6-часовом окне;
    - ответы игроку не позже 10 с и ни одного молчания;
    - восстановление после сбоев;
    - траты не больше `daily_llm_usd` за UTC-сутки.
  - Выключенный житель — FAIL. Итог печатается JSON до 2 КБ.
- **Готово, когда:** на работающем мире обе команды печатают PASS/FAIL с числами из свидетеля.

### 2.3 Развёртывание по `DEPLOY_NEW_WORLD.md` (M) — сделано в коде
- **Как.**
  - Развёртывать с последнего зелёного `main` (`make check` на сервере перед Ф10).
  - Перед развёртыванием в `tools/prepare_resident.py` и `tools/prepare_demo_resident.py` поменять порядок: сначала атомарно сохранить credentials (0600), потом INSERT аккаунта, потом копировать профиль. Повторный запуск доводит незавершённые шаги, если секрет сохранён. Сейчас частичный сбой оставляет аккаунт с потерянным паролем, а чинить его правилами запрещено.
- **Готово, когда:** `ro doctor world` PASS, `ro status` показывает трёх жителей «онлайн; … решил сам (LLM)», в `decisions.jsonl` у каждого есть `MODEL_DECISION` и связанный `GOAL_OUTCOME done`.

### 2.4 Жизненный цикл чата (S) — сделано в коде
- **Проблема.** При файле `STOP` служба `ro-chat` выходит с кодом 0, `Restart=always` за 15 с исчерпывает лимит, и служба уходит в failed. `ro start` её не поднимает. Если остановка случилась посреди ответа, флаг `CHAT_PENDING` остаётся, и мозг жителя крутится в `supervisor.py` бесконечно.
- **Как.**
  - В `chat.serve` на `STOP` — пауза вместо выхода, плюс обработчик SIGTERM.
  - В `deploy/ro-chat.service`: `PartOf=ro-world.service`, `StartLimitIntervalSec=0`.
  - `ro start/stop` управляют обеими службами.
  - `CHAT_PENDING` хранит pid и deadline; мозг удаляет устаревший флаг.
  - Строка состояния чата в `ro status`.
- **Готово, когда:** после `ro stop` и `ro start` фраза игрока получает ответ без ручных шагов.

### 2.5 Разговор не останавливает жизнь (S, затем M) — сделано в коде
- **Проблема.** Любая фраза рядом отменяет охоту или follow. Мозг потом 120 с стоит без LLM и без привычек (`mind.choose`), хватает даже шёпота с другой карты. Игрок, пишущий раз в 2 минуты, держит жителя замороженным. Ответ ждёт общий моторный lock, поэтому во время продажи игрок получает `WRITER_BUSY`.
- **Как (S).**
  - `CHAT_PENDING` ставить после решения и только для follow, walk_to, meet и «стой».
  - Пауза мозга — только пока идёт разговор с игроком рядом, которому житель реально ответил, и не дольше 30–45 с. Привычки при этом работают.
  - Реплики того же собеседника не рвут цель, согласованную в чате.
  - Оплаченное решение сохранять в `model-intent.json`, а не выбрасывать.
  - Дешёвые проверки (`CHAT_PENDING`, активная задача) делать до платного вызова.
- **Как (M).** Отдельный речевой слот тела для всех жителей (executor уже разводит речь и мотор), голосование о встрече вне writer-lock.
- **Готово, когда:** фраза игрока посреди охоты получает ответ, а охота продолжается, без `CHAT_INTERRUPT`.

### 2.6 Журнал шлюза и логи (M) — сделано в коде
- **Проблема.** Каждый кадр телеметрии (1 Гц) пишется в SQLite: 130–220 МБ в сутки на жителя. `evaluate()` 20 раз в секунду читает всю таблицу actions, и на старом VPS это уже давало таймауты status. Логи пишутся дважды и без ротации. Сбой fork или запись при ENOSPC (`supervisor.py`, запуск детей вне try) роняет всех жителей.
- **Как.**
  - Телеметрию держать в памяти, в БД писать только переходы.
  - Не журналировать read-only запросы, добавить индекс `(resident,state)`.
  - Раз в час чистить старые terminal-записи и делать `incremental_vacuum`.
  - Ротация логов детей, `logConsole 0` в профилях, logrotate для rAthena.
  - Запуск каждого ребёнка в try.
  - Предупреждение о месте на диске в `ro status`.
- **Готово, когда:** за 6 часов `journal.sqlite` каждого жителя меньше 20 МБ, status отвечает до 0,5 с.

### 2.7 Бюджет и контекст (M) — сделано в коде
- **Проблема.**
  - Контекст одного решения ≈ 8,4 тыс. токенов (≈ $0,0024), а ТЗ разрешает 1,5 КБ.
  - Меню LLM выросло до 21 действия, включая заведомо недоступные `heal` и `party_invite`.
  - Темп только растягивает паузу, а действие длиннее паузы её поглощает. По симуляции «городской» день исчерпывает $2 к 9–13 UTC.
- **Как.**
  - **Один сборщик контекста** для решения, чата и голосования, с жёстким лимитом: 1536 Б для решения, 1 КБ для чата. История задач — до 3 строк по-русски без id. Диалог — последние 4 реплики с текущим собеседником.
  - **Меню LLM на v1** — ключ `llm.menu` в конфиге, по умолчанию 9 исходных действий и `respawn`. Каталог Hermes остаётся доступен оператору через `ro actions`.
  - **Регулятор трат.** Следующий платный слот = средняя цена / (остаток денег / время до полуночи UTC), отсчёт от конца действия, резерв около 25% на чат.
  - **Учёт.** Токены в `ro status`. Тест на сутки симуляции: деньги остаются к 23:59 и есть не меньше одного решения в час на жителя.
- **Готово, когда:** `ro accept --window 6h` показывает траты, пропорциональные времени суток, а `tokens_in` решения — не больше 1,5 тыс.

### 2.8 «Пойдём со мной» с настоящим игроком (S, затем L) — сделано в коде
- **Проблема.** Позицию цели код берёт только у свидетеля, а свидетель пишет лишь персонажей из `residents.registry`. Персонаж владельца сразу получает `NO_TARGET_WITNESS`. Follow идёт шагами с 5-секундным свидетелем и теряет идущего игрока.
- **Как (S).**
  - На время follow временно вносить гостя в `residents.registry`. Нужен узкий пользователь MariaDB с INSERT/DELETE только в этой таблице (решение владельца, §2 ТЗ).
  - Без такого пользователя — позиция из наблюдений тела с пометкой «слабее».
  - Не повторять `NO_TARGET_WITNESS`.
  - Ответить до ts+10 с, а проверять свидетелем в отдельном окне 20–30 с.
  - Отрицания («не иди») не запускают движение.
- **Как (L, этап 4).** Нативный непрерывный follow в плагине: Python только собирает пробы, цель считается потерянной примерно после 20 с невидимости.
- **Готово, когда:** вы своим персонажем говорите «пойдём со мной», и по свидетелю житель не дальше 5 клеток в 70% и более проб за 3 минуты.

### 2.9 Повторы и честные итоги (S) — сделано в коде
- **Проблема.**
  - Защита от повторов считает прерванное или проваленное дело сделанным: подменяет его на idle с «уже сделано» и включает тихое окно на 5 минут. ТЗ §4 разрешает до 3 попыток.
  - Ретраи охоты прячут настоящий код (`TEST_WINDOW_LIMIT`) и перезапускают охоту после NEEDS_REST или DIED.
- **Как.**
  - Защиту от повторов применять только к `done` и только пока житель ещё на месте. Для провалов — счётчик из 3 попыток, без учёта `CHAT_INTERRUPT`.
  - В охоте повторять только дорогу. NEEDS_REST, DIED и «нет партии» не повторять.
  - Охота с убийствами, но без полного срока, получает итог `HUNTED_PARTIAL`.
  - Настоящая причина видна модели и в `ro status`.
- **Готово, когда:** в `decisions.jsonl` нет `TEST_WINDOW_LIMIT`, и прерванный разговором `walk_to` при повторном выборе выполняется.

### 2.10 Бэкапы (S) — сделано в коде
- **Как.**
  - Суточный дамп БД персонажей и `/var/lib/ro-world/*/` (память, дневники). Хранить 7 ежедневных и 4 еженедельных копии.
  - `myisam_recover_options` в MariaDB.
  - Запуск — из потока supervisor, без cron.
- **Готово, когда:** восстановление дампа на тестовую БД проходит, и в `ro doctor world` видна дата последней копии.

## Этап 4. Развитие (только после PASS этапа 3)
Каждая новинка — со своим живым доказательством по свидетелю и без регресса `ro accept`.
1. **Нативный непрерывный follow** в плагине (L).
2. **Поддержка напарника как отдельный навык** `support(partner, minutes)` (L):
   - вход только если партнёр онлайн, на той же карте и ближе 10 клеток;
   - доказательство — убийства партнёра по свидетелю плюс собственные позиции рядом, а не рост job level за окно;
   - самооборона `attackAuto 0`;
   - совместный старт через `meeting.py`;
   - дуэт включается через overlay.
3. **Развитие персонажа** (M):
   - очки статов и навыков распределяет плагин по политике, которую выбирает LLM;
   - плагин хранится в репозитории или подключается явным путём из `vendor/openkore` с проверкой в `ro doctor world`, не абсолютной ссылкой.
4. **Смена профессии** как многошаговая цель: дорога к NPC, диалог, проверка класса по свидетелю (L).
5. **Каталог мест охоты** по уровню вместо одних порингов на prt_fild08 (M).
6. **Каталог действий Hermes в меню LLM.** Единый реестр — источник схемы, промпта, availability, валидации и доказательства, не больше 12 действий одновременно (M).
7. **Рефлексы тела вне охоты** — зелья и самооборона в городе и на дороге (S).
8. **Тела, мозги и чат не от root**, отдельный пользователь MariaDB для чтения (M).
9. **Архив устаревших документов:** один `STATUS.md`, `docs/` только актуальное (S).
