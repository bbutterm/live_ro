# Несколько ИИ без конфликтов

## Рекомендуемая схема
**Hermes — интегратор и VPS QA; остальные модели — независимые authors/reviewers через GitHub issues и PR.** Не запускать их всех в одной папке и не давать каждой администрировать один сервер.

1. Интегратор закрепляет контракт и назначает issue одному writer; блокировки видны в issue.
2. Каждый worker создаёт branch `task/<issue>-<topic>` и отдельный worktree/clone. Один issue = один PR.
3. В issue: allowed paths, forbidden paths, контракт, зависимости, реальные критерии и бюджет. Нельзя 'заодно' менять чужой модуль.
4. Authors тестируют офлайн; другой ИИ делает read-only review PR. Изменение контракта проходит через интегратора.
5. Интегратор объединяет PR последовательно, запускает совокупные тесты и проверяет на VPS. Никто другой не переключает deployment checkout или не создаёт миграции на работающей БД.
6. Закрывать задачу только по соответствующему доказательству. Unit-ready и runtime-accepted — разные статусы. Нет автоматического merge/deploy.

## Безопасные параллельные части вехи A
- `server/witness/`, `server/schema/`, `tests/witness/`: NPC-свидетель и отдельная SQL-миграция; не применять самостоятельно.
- `packages/witness_reader/`, `tests/witness_reader/`: SELECT-only reader, cursors, follow/wait CLI на независимых фикстурах.
- `packages/evidence/`, `tests/evidence/`: offline анализатор/экспорт результатов; не имитировать доказательства игры.
- `checks/qa/`, `tests/qa/`: независимый QA проверки readiness/auth/доступа конфигов без изменения продуктов.
- `ops/`, `tools/`, интеграционные tests: только интегратор. Он завершает tester и runtime.

Все эти модули допускают отдельную разработку сейчас, но интеграция witness → reader → evidence выполняется по gates. Схема v1 в contracts/witness-v1.md: изменение общей схемы без согласования запрещено. Плагины body, планы, память и голос — будущие задачи после принятых вех, не текущая параллельная работа.

## Готовый промпт для любой модели
```text
Работай над bbutterm/live_ro, только issue <URL>. Прочитай AGENTS.md и docs/COLLABORATION.md. Сначала сверяй main и контракт своего issue. Создай отдельную ветку/worktree. Пиши только allowed paths. Не трогай чужие ветки, VPS, БД, секреты, submodules и контракты. Выполни офлайн-тесты, открой PR, укажи фактические команды и результаты, ограничения и что ещё не проверено в игре. Не merge и не deploy.
```

Отдельные репозитории сейчас не нужны: monorepo с контрак­тами и непересекающимися owners проще. Вынос в отдельный package/repo оправдан позже для реально переиспользуемой библиотеки, а не ради количества моделей. Git worktree изолирует файлы, но не базу/порты/процессы — общий стенд всегда один владелец.
